    Deviations¶

    Where OpenInterceptor knowingly differs from the original game, or uses an engine value where the original's is unknown, and why. A deviation on the record is a decision; an undocumented one looks like a bug.

    ID Deviation Why Stage
    DEV-001 Default keys for actions the original left undocumented: M match speed, W cycle missile, Kp4/6/8/2 VCT slides, Q/E roll, LeftControl also fires beams, C mouse flight. These actions exist in the original's bindable list but their release defaults are not documented anywhere found; Q/E and LeftControl help keyboards without a keypad. 1
    DEV-002 Navigation points in scenarios (nav: {<name>: …}), cycled with N, shown on the MFD Nav page and as an on-screen marker. The original has no in-mission nav points (travel happens on the strategy map). Mods need them; the test arenas use them to find the alien and pirate groups. 1
    DEV-003 Gamepad support with an XInput-style layout. The original supported DirectInput joysticks and rudders only. 1
    DEV-004 Mouse controls are rebindable (beams/missile via the bindings; steering range via mouse_range in bindings.yaml) and mouse flight is a toggle (C). The original fixed them; a toggle avoids the mouse fighting the menus. Steering direction follows the readme (cursor down = nose down). 1
    DEV-005 Hardware 3D with per-vertex lighting instead of the 16 shade palettes. The shade palettes served the 1998 software renderer; palette 0 (full brightness) gives the texture colours. 1
    DEV-006 Wide-screen: a cockpit's design space (640×480 for the originals) is scaled as large as fits and centred; the 3D view fills the window. Cockpits may declare their own design (e.g. 1920×1080) and may be 3D models. Modern displays are not 4:3; modders replace cockpits with HD, widescreen or 3D ones. 1
    DEV-007 Multiplayer deferred, possibly never implemented. Not needed for single player or modding. 7
    DEV-008 Original beam Range is kilometres (Range=4 in GameSettings.ini → 4 000 m, when inherited through inherit: original:…). Since mod format 2 a mod's range takes a unit (2.4km, 350m; a plain number is metres), replacing the Stage 1 RangeMetres key. Confirmed in app 0.21.0 — no longer a deviation. The original's program gives a bolt a lifetime of Range × 1,000,000 / Speed ms, so Range is in km (verified, Interceptor.exe). Kept on the list for the reading of inherited values; a mod's own range takes a unit. 1 → 4 (confirmed)
    DEV-009 Missile turn rate and lock time — since app 0.22.0 from the original program in interceptor: every homing type turns at most 2.5 rad/s (turn_rate: 143.2) and leads its target as if it flew at 200 m/s (lead_speed: 200), and the lock time comes from the ship's sensor (systems.sensors.lock_time, 2.5 s for the first targeting system; verified). Still the engine's: the missile's own lock_time for a ship whose sensor sets none (the original cannot lock without a sensor), the missile's throttle (the original slows a missile that is more than 5° off its target and speeds it up again on target, and flies it straight for its first 250 ms), and which sensor each hull carries (derived: the first). Before app 0.22.0 the original's guidance and lock were not decoded and each missile had engine values. The guidance routine and the sensor table are now read as data (notes/re/flight §5.2). The missile throttle is not built yet (Track A, A5). 1 → 4 (A5)
    DEV-010 Proximity fuse fires on a near miss: inside ProximityRadius and moving away from the target. A hit inside the target's collision shape deals ImpactDamage. Firing as soon as the radius was entered meant impacts never happened. 1
    DEV-011 Hull energy, protection and acceleration — since app 0.21.0 mostly the original's: every ship shares the original's 1000-point energy pool refilled at 0 / 7 / 10 / 15 / 22 per second (power.energy, energy_recharge; verified); shields and armour come from fitted equipment (app 0.15.0) with the difficulty factors (app 0.21.0, verified); the player's acceleration is the fitted engine's thrust (fitted: {engine: …}, its Special in kN) × throttle × engine power / mass under flight.drive (verified). Still engine values: which engine each hull carries by default (derived), and acceleration for classes without a thrust figure. Before app 0.21.0 the pack gave each hull its own energy, recharge and acceleration (engine estimates). The original's routines now read as data (notes/re/flight, facts only); only the default fit is not in the data. The default campaign keeps its own per-class values. 1 → 4 (A1/A6)
    DEV-012 Alien, freighter and capital flight values — since app 0.21.0 from the original program: AI ships move by their class's drive factor S (ai_speed, top speed S / 2: fighters 500, Wraith and Spectre 350–400 + 40 per level, Phantasm 450–500 + 30 per level, freighters 100–174, Patton 100, held to 100–500; verified) and turn at the program's fixed per-class rates (ai_turn, verified; which axis is which is derived). Still estimates: the classes' max_speed, acceleration and turn rates where a player flies them, the drone's and Harbinger's mapping to the program's classes (derived). The original file has flight values only for the three X-COM hulls; the others are coded per class in the AI's constructors and turn table, now read as data (notes/re/flight §5). AI ships in the original ignore mass, engine and MaxSpeed, and so do they here. 1 → 2 → 4 (A6)
    DEV-013 Missile lock cone — since app 0.22.0 the original's: the sensor's cone (lock_angle: 2.5 for the first targeting system, 2.5°), doubled once locked (flight.lock_hold: 2), within the sensor's range (3 km), and a part-built lock runs down as fast as it built (flight.lock_decay; all verified: LockAngle is in millidegrees). No longer a deviation in interceptor; the default campaign keeps its 10° cone. What remains approximated: DEV-074, DEV-075. The original's SensorsSetting LockAngle units were not decoded before app 0.22.0. Kept on the list for the default campaign's engine value. 1 → 4 (A5, resolved)
    DEV-014 Cockpit ↔ hull mapping A = Lightning II, B = Firestar, C = Super Avenger. Derived (one cockpit per hull), not confirmed. 1
    DEV-015 One-shot inputs are carried across frames that run no simulation tick (Controls::carry_unconsumed). On high-refresh displays some frames run no tick; a key press would otherwise be lost. Not an original behaviour, an engine correctness fix. 1
    DEV-016 Esc opens a pause menu (resume, restart, back to launcher) instead of resetting the MFD. The testbed needs a way back to the launcher; MFD pages cycle with </>. 1
    DEV-017 Keyed cockpit pixels become transparent black, not transparent cyan. Filtering would otherwise blend cyan into the edges of the art. Visual result matches the original. 1
    DEV-018 ~~"Ignore my target" and "retreat" wingman orders both mean "form on me"; "evasive" is not bound.~~ Resolved in Stage 2: every wingman order has its own behaviour (formation, attack my target, fire at will, 10 s evasive weave, retreat and hyperspace out) and evasive is bound (Shift+E). Distinct behaviours arrived with the Stage 2 AI. 1 → 2
    DEV-019 Newtonian flight model by default: throttle is thrust, ships coast at zero throttle, Z reverses thrust, a held brake (B) retro-thrusts to a stop, MaxSpeed caps speed, turning does not steer the velocity. flight: {model: assisted} restores the arcade model (throttle = target speed, automatic slowing, drift damped). The original's flight model is not documented and felt arcade-like; the project owner chose physics where deceleration only comes from thrust. Keeping both as data lets each campaign choose. 1
    DEV-020 Flight computer (speed hold): match speed (M) and every AI pilot fly a held forward speed through hold_speed, which thrusts and brakes within the hull's own acceleration and also cancels sideways drift. Under newtonian physics AI pilots need a way to manage speed that obeys the same limits as the player; cancelling drift keeps AI dogfights readable. 1 → 2
    DEV-021 Arena edge: ships reaching flight.arena_radius (default 60 km) are halted against it ("ARENA BOUNDARY"). Under newtonian physics a coasting ship would otherwise drift away for ever; outside testing this should rarely be reached. 1
    DEV-023 Overlay polygons are depth-biased instead of drawn in BSP order; coplanar overlapping faces are found geometrically, the original overlay flag only decides which is on top. Translucent-flagged polygons are drawn opaque for now. A depth-buffered renderer cannot use painter's order per model; the same pass then also serves mod OBJ decals, which have no flag. The opacity meaning of the flag is not confirmed. 1
    DEV-022 Per-asset overrides and --extract: any original model, texture, image or sound is replaced by a pack file at its override path; the extractor writes every original asset at those paths in OBJ/PNG/WAV. The modding objective: HD and 3D replacements without touching or redistributing the originals (compare XWVM, Modding). 1
    DEV-024 Power budget, start levels and system power steps — since app 0.21.0 the interceptor campaign follows the original: ships start at beam C / shield C (verified); the settings and switched-on systems cost engine power, 1/12 per step (flight.drive.power_cost, verified), not a shared budget, so power.budget is set out of reach (20); the cloak draws 6 steps, half the engine's power (verified); shield balance routes the one recharge stream (power.balance: share, verified). Still engine values: the tractor's 2 and ECM's 1 steps (derived). The default campaign keeps budget: 6, start C / C and balance: shift. The original's charge-rate tables are in GameSettings.ini; the start values, the engine-power cost and the balance routing are in its program (notes/re/flight §2–§3, §5). All are power / systems / flight data. 2 → 4 (A3)
    DEV-025 Firing drops the cloak (beams or a missile), with the message "CLOAK DROPPED". Prevents an invisible ship from attacking with impunity; the original's exact rule is unknown. Cloak lock-break by difficulty level waits for 2.8. 2
    DEV-026 Hyperspace countdown of flight.hyperspace_time seconds (10 in interceptor, 8 in default), doubled while the hyperdrive is damaged; pressing H again aborts. The original's countdown length is not documented (derived). 2
    DEV-027 Default keys for tractor, cloak and ECM: Shift+T, Shift+C, Shift+J. The original's key list has no documented default for these; Shift chords keep the plain T, C and J free. Rebindable in the controls menu. 2
    DEV-028 Gamepad modifier layer: holding the left shoulder (LeftShoulder) switches the pad to a second layer (LeftShoulder+A hyperspace, LeftShoulder+DpadUp power to beams, …); a button used as a modifier does nothing on its own. A controller has far fewer buttons than the keyboard has keys; chords make every action reachable from the pad (extends DEV-003). 2
    DEV-029 System condition thresholds (the engine's standard table): above half its hit points a system works fully, at half or below at half effect, at zero it stops until repaired back to 25 %, below −destroy_below × hit_points (−50 %) it is destroyed for the battle. Repair takes the worst system first. The original shows damaged / inoperative / destroyed systems and repairs them, but its thresholds and repair order were not in the data (derived). Since app 0.22.6 the original's repair is data and interceptor uses it (verified, notes/re/flight §4.3): damage.repair_order — 2 points per second, 4 with a damage control computer, to the first of engine, hull, shield generator, flight control, hyperdrive, sensor, mounts, specials — and destroy_below: 0 (a system at 0 is never repaired). No longer a deviation in interceptor; the default campaign keeps the engine's rule. Static objects never repair their hull (derived). 2 → 4 (#116, resolved in interceptor)
    DEV-030 Mod files are a strict subset of YAML, read by an in-crate reader (formats::yaml): no tabs, anchors (&a), aliases (*a), tags (!!str), multiple documents, complex keys (?) or plain scalars continued over several lines — each rejected with its line number. Every scalar stays text until the schema types it. Mod files moved from INI (format 1, no longer read) to YAML (format 2). YAML gives modders nesting, lists and comments that INI lacked, and is what OpenXcom modders know. A full YAML library was not taken: the project's dependency policy avoids dependencies for what the codebase can do, serde_yaml is unmaintained, and full YAML's implicit typing (no → false, 1.10 → 1.1) and anchors surprise modders. The subset covers every construct the mod files need; the original game's own INI files are still read as INI. 2
    DEV-031 AI skill model: enemies aim with an error of up to (1 − aim) × 8°, re-picked every reaction seconds, fire in burst/pause cycles inside a fire_cone, and check behaviour transitions 4 times a second. The original's AI is hard-coded and its accuracy model unknown; this model is data, so each campaign tunes it per difficulty level. 2
    DEV-032 Interceptor enemy behaviours — since app 0.22.0 the attack itself is the original's (verified, notes/re/flight §5.1): every fighter behaviour inherits original_attack — fire cone 1.5° – 2.5° and range 2 – 2.5 km by level, missiles within half that range and at least 5 s apart, lead only within 1,750 m, the accuracy aim model at 50 % (lead-time error, 15 – 25 m misses below 50 %, sluggish turning on a failed roll), and trigger intervals for the Wraith and Spectre (0.5 s + 60 ms per level below superhuman) and the drone (1.5 s + 50 ms per level). Still derived: when each class breaks off, jinks or flees, the Harbinger's towing, which original hull class each behaviour stands for, and the X-COM pilots' and Harbinger's own values. The original's AI is code, not data; its fighter attack routine is now read as data. The other agent states (breaking off, fleeing) and the non-fighter agents are not traced yet; those parts follow the strategy guide's descriptions and were tuned in the testbed (and with --soak). What remains approximated: DEV-075 – DEV-078, DEV-080. 2 → 4 (A7)
    DEV-033 3D cockpit instruments drawn in perspective on the dashboard (anchors) and an in-game cockpit layout editor (F12) that saves an addon. Engine extensions for modding: the original has only 2D cockpits. XWVM's 3D cockpits show instruments on in-cockpit screens the same way. 2
    DEV-034 Explosions are engine fireballs (size, duration, colour, optional shock-wave ring per effect) instead of the original's XSPT sprite animations; which original wreck set each class uses follows the set names. XSPT pixel runs are not decoded yet; the 28 wreck sets' names and chunk meshes are verified from Interceptor.exe, the class mapping is derived. Effects are data, so sprite explosions can replace the fireballs later without rule changes. 2
    DEV-035 Module placement on the original bases is derived: which of the X-COM base's 33 and the alien base's 28 attachment points carries a turret, shield generator, hangar or pod. Hit points come from the original M_XCOM* / M_ALIEN* sections (verified); destroying the hub destroys its modules. Since app 0.22.4 the interceptor bases have the original's shield rules (verified, flight notes §8.2 – §8.3): one pool sized by the generator type (2,000 X-COM Type1, 3,000 alien Type2), 2 points per second, modules covered by it; when the last generator falls the pool drops to 0 (app 0.22.6, verified, unknowns §8; 0.22.4 kept it). The outposts and ore plants have their own pools of their chart's SD at 2 per second (app 0.22.6, verified). The original assembles bases on the strategy layer (Stage 4), so their battle layout is not stored; the cascade rule follows the strategy guide's description (derived) — no code was found in the original that destroys a hub's modules with it (unknown). Placement is modules: [{slot, class}] data. Since app 0.22.11 the pirate base and the arms dealer have the original's turret tables (positions, facings, ranges, arcs; the base's 75 − 5d % chance per turret; verified), and the alien base its connection point and minefields (DEV-088). 2
    DEV-036 Special missile behaviours are engine models of the original's descriptions: Sidestep turns twice as hard inside 600 m and weaves; Parallax decoys lure at 80 % per second within 2.5 km; Passive Cloaking waits for prey within 800 m; Doppelganger copies are fragile and short-lived; mines blast four times their fuse radius. The original's guidance code is not data; names and one-line descriptions are all that is known (derived). Every number is a missile key or an engine constant documented on Missiles and mines. 2
    DEV-037 Shield rings on the radar scopes (front scope = fore shield, rear = aft; green / amber / red, blinking when down), top-bar text placement in the interceptor cockpits (message in the lit band, throttle line, power and systems in the two strips below), and since app 0.15.1 the ship status display (ship_status): the craft from above tinted by hull, inside fore and aft arcs of up to three shield bands each, in the round ship display of cockpits A, B and C. The rectangles are measured from the cockpit art (verified pixel bounds); what the original showed in each strip and the ring thresholds are derived from the player's description of the original HUD. The ship status display is a user request after a playtest (the round display showed nothing): its look follows X-Wing's shield display, not the original's (what the original drew there is unknown), and its rectangles in A, B and C were placed by eye (derived). 2, 6
    DEV-038 Point defence is the engine's: which ships carry point defence (the Patton, the X-COM freighter, the bases; the dreadnought and the stations) and its numbers (range 900 m–1.2 km, 3–4 shots/s, 35–40 % kill chance, 3–4 energy per shot). Point defence also shoots at decoys. Known to differ from the original (verified): the original has no automatic point-defence turret; a beam bolt that strikes a missile applies the beam's damage with a 90 % chance and destroys a missile with fewer hit points (HitPoints clamped to 10 – 500). Its station defence modules are not traced. The point_defence keys predate the analysis and give convoys and bases a defence the default campaign relies on. Matching the original would mean no turret in interceptor and missiles that bolts can hit; not built yet (Track A, A7). 2 → 4 (A7)
    DEV-039 Probes act in battle: a sensor probe extends its side's radar to 8 km around it; an ECM / jamming probe halves hostile radar range and missile-lock speed within 2.5 km. The original launches probes from the strategy map; their battle effects and numbers are derived (mesh names SENSPROB, ECMPROB verified). Data: probe: {sensors, jamming}. 2
    DEV-040 Mission arrivals belong to the role (at: {distance, bearing, from, spread} and arrive: <condition>) instead of a separate arrivals: map as first designed. One place per group keeps a role's composition, position and timing together; a role without arrive: enters at the start. Waves add members later. 3
    DEV-041 Interceptor mission compositions are derived: the five implemented mission types (xcom_base_defense, defend_freighter_convoy, deep_space_encounter, attack_alien_outpost, destroy_alien_probe) use the original's own names, briefings and debriefs by key (@orig.*, read from the CD), but which classes appear, how many, where and in what waves are estimates, sized early-war so every level is winnable and losable (checked with --soak). The original composes battles in code and grows them with campaign progress (Stage 4); compositions are missions: data. %s in original briefings awaits the strategy layer. 3
    DEV-042 Process: Rapid Prototyping run as an implementation project. The project follows the Rapid Prototyping workflow (SpecItOut proposal P65), but until sio supports a prototype kind the manifest declares kind: implementation, with spec pointing at this worktree's docs/specification (Definition and Specification 1.0.0). The sio client does not yet support the prototype kind; the implementation kind lets issues cite requirement IDs now. Process
    DEV-043 Shot launch speed. The engine's default is plain physics (flight: {bolt_frame: world, bolt_inherit: true}): a bolt leaves with the ship's velocity plus the muzzle's turn velocity plus its muzzle speed, then flies straight. In the original a bolt's velocity is Speed along the aim direction without the firing ship's velocity, and it lives Range / Speed (verified). Since app 0.22.0 flight.bolt_inherit: false reproduces that, and interceptor sets it; the AI's lead and the HUD's lead indicator follow the switch. No longer a deviation in interceptor. Physics stays the default by decision D1 (R-CMB-021), so the default campaign plays as before; bolt_frame: ship remains the arcade alternative. 3 → 4 (A2, resolved)
    DEV-044 Interceptor lighting adds a rim light and distant dots (flight: {lighting: {ambient: 0.30, sun: 0.85, rim: 0.35, distant_dot: 4}}): hulls seen edge-on are outlined, and craft smaller than 4 px on screen that are on the radar are drawn as a dot in their radar colour. An engine choice for visibility (F-HUD-007: "it is difficult to see other fighters"). Ambient and sun match the engine's earlier fixed lighting; the original's look is otherwise unchanged and the keys are data. 3
    DEV-045 Interceptor hazards are engine models with derived numbers: the black hole pulls with 1/d² (pull at 1 km, capped at 20 ×) and destroys craft inside its radius; the ion storm keeps a fraction of radar range and halves lock speed; asteroid fields are scattered, slowly turning objects. The interceptor testbed scenarios use pull: 12, radius: 450 and sensors: 40%. The original's belt and black-hole battles are built in code; their pull law, numbers and sensor effects have not been measured. All are hazards: data (R-MSN-009). 3
    DEV-046 The strategy format as built is a simpler subset of its design: one start: section instead of starts; base_types.max_distance (map units) instead of a placement expression; plain numbers for upkeep, maintenance, salary and costs (only incomes, expenses, the research rate and prerequisites are expressions); raids: with fixed missions instead of squadrons, flight plans and generated missions; pilot ranks by experience thresholds; fitting is best available from the store (app 0.7.2) without fitting rules. Stage 4 first makes every rule playable end to end with the default campaign; the richer keys of Format: strategy layer are added when the interceptor strategy data (4.12) and logistics (4.14 – 4.17) need them. 4
    DEV-047 The default campaign's strategy texts are plain English in resources/default/strategy/*.yaml, not text keys. The strategy layer was written ahead of its translation; moving the names and descriptions to text/en/ keys is a data change for a later pass (R-STR-010 Open note). 4
    DEV-048 A battle runs on after its result: the verdict and computer voice come at once, and the debrief waits flight.debrief_delay (30 s by default; Enter skips it; a retreat shows it at once). User request (playtest, app 0.7.4): to watch the final explosion. An engine choice: the original's own timing is not measured here (unknown); the delay is rules data, so a campaign can set 0s. 3
    DEV-049 Logistics as built simplifies its design: the nearest supplier is measured in a straight line between systems, not by lane (R-STR-013); convoy ambushes are auto-resolved as per-vessel losses (since app 0.9.2 only when the campaign has no logistics.ambush_mission or the player declines to fly the escort), and an attacked survey ship is lost on a fixed 50 % roll, instead of generating battles. Closed in app 0.19.0 (c28fc2c): facility placement was a fixed rule per role and is now the design's placement: condition (each role's rule a default condition, Role::default_placement; the manufacturing rule reads bases > 0 and lane_distance(system, nearest_base) <= 2 rather than the design's owned(system) and …); storage limited only mining facilities and now limits every facility. One facility of each type per system stays a fixed rule, not the design's max_per_system key. Closed in app 0.20.0 (9064f59): the attacked survey ship's fixed 50 % — it now waits at the site and fights logistics.survey_mission, flown or auto-resolved with logistics.survey_loss (default 50 %, data; decision D3). App 0.9.0 (ff9d8fc): the smallest version of the design that plays the whole chain. The placement conditions followed in app 0.19.0 (Batch 4.1); flown ambushes followed in 0.9.2; the survey battle and its loss chance as data in 0.20.0 (Batch 4.2). The straight-line nearest supplier remains as built. Default campaign only; the interceptor campaign has no logistics. 4
    DEV-050 The interceptor strategy layer's estimates are derived: the start (date, pilots, craft, stock), the generated map's number of systems, delivery and salvage, hull speeds, missile rounds, module groups and effects, the X-COM base type's cost and hub sensor range, corporate funding and the raid rolls and targets are authored in packs/interceptor/strategy/campaign.yaml, each marked DERIVED; the pilot rules and mission score points are authored there too, from the design analysis, without the mark. The tech-id table in references.yaml is read from the player's executable by a layout that is itself derived (12-byte entries: R_ name pointer, string id, tech id); ids 75 and up are not in it and are left out of conditions; research unlocks are not authored (items, hulls and modules are gated by their own TechRequired). App 0.8.0 (c64d178, plan item 4.12): research sizes and prerequisites, costs, production times and maintenance are inherited from the player's GameSettings.ini (verified as data, no values in the pack); what the original keeps in code or its manual describes only loosely is estimated, from the design analysis.     DEV-060 Tier 2 scripts as built differ from their design (app 0.18.0, decision (c), Scripts): (1) a file declares no context — each hook compiles the functions it reaches against its own context, so a function no hook reaches gets only the structural check (balanced braces, defs, parameters); (2) there is no counter action — lasting state is campaign flags (set_flag) and a behaviour's object variables (vars:, set_var, var(name)); (3) do: script also flies a manoeuvre (fly:, default attack, with the state's usual parameters) while the script decides; (4) battle scripts run only from mission outcomes, at the battle's end — there is no per-tick mission hook; (5) for each exists only in the battle context (over a role's members); (6) statements are line-based (one per line or ;-separated); (7) a value-returning function that ends without return gives 0 / false. (7) Avoids a run-time "no value" error in a language whose mistakes are all meant to be load errors. 3
