    Coverage matrix¶

    Status: design check, 2026-11-10. For every system of the original (analysis): the construct that expresses it, where the interceptor mod gets the data, and the simplified equivalent in the default campaign. The second table goes the other way: features the default campaign adds, and what they mean for interceptor. A row with no construct would be a gap in the format. There are none; the open items at the end are data the original hides in code, which must be recovered, not format features that are missing.

    Data source key: INI = imported from the original INI files by inherit: original:… (mod files themselves are YAML); TXT = original text by reference; AUTH = authored in the mod from the strategy guide and play-testing (the original hard-codes it); EXE = a table read from the executable during analysis and written into the mod as data.

    Open items (data the original keeps in code)¶

    These need the strategy guide, careful play of the original, or both; each becomes a work item in Stage 5 with its source recorded (verified/derived) in the mod's comments:

    1. The meaning of each MissionScores index (values are data, indices are code).
    2. Exact squadron compositions per mission type, tech level and difficulty (the guide's tables are partly illegible).
    3. Star count, planet size and sensor-radius tables for map generation.
    4. Salary, recruitment and psionics-by-rank modifiers.
    5. The alien tech-level cost mapping and the Doomsday cost/time columns.
    6. Station hit-point chart meaning (HP1..HP4, SD).
    7. The three-ring effect meshes (1ASH* etc.): shield flash or jump effect.
    8. Whether overlay-face low bits on station hubs are state groups.

    Each is a data question with a reasonable fallback (the guide's legible values, or a documented estimate marked derived), so none blocks the format or the stages.
