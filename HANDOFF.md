## 2. How this project is run (the user's standing directions)

- **Objectives, in order:** a data-driven *modding toolkit* first (X-COM: Interceptor is
  one content pack), a *Rust teaching example* second, *compatibility* with the original
  (played from the player's own data) third.
- **Rapid prototyping, no approval gates:** feature request → spec on the docs site →
  GitHub issues → implement → docs updated **with** the code → push. The user works
  through manual-test issues and reports playtest findings.
- **Never commit original content** in any form (models, textures, images, sounds, music,
  video, text, INI, executables, dumps, extracts, screenshots, conversions). Original
  binaries are read as data only. Scratch exports and screenshots go in a temporary
  folder. Docs may cite facts (names, ids, coordinates, stat values) but never reproduce
  art or text. X-COM values are *inherited from the player's files at load time*: the
  pack holds section names, ids, `@orig` keys and facts needed to reference data.
- **Every feature must work in the original-free `default` campaign** (generated by
  `tools/default_assets/`), not only in `interceptor`.
- **Every new rule/pack key** is documented on the docs site's Modding pages in the same
  change. Facts derived from the original are marked verified / derived / unknown.
- **Code bar:** comments for a Rust beginner (`//!` module docs, `///` on public items),
  `sim` deterministic at 60 Hz with no macroquad, errors not panics, no globals, `unsafe`
  only at FFI, `cargo fmt` + `cargo clippy --all-targets` clean, unit tests for all
  testable logic, manual test cases (docs `implementation/testing/manual-tests.md`) for
  the rest.
- **Commits** end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; push
  after each commit; bump the patch version per change set (minor per feature).
- **Delegation pattern that worked:** implement + gate + commit myself; send a docs agent
  (general-purpose, background) after each batch with the commit list, asking it to
  update spec/modding/user guide/architecture/implementation/tests, add manual cases to
  the manual-test issues (#74–#97), comment on implementation issues, and report code
  problems it notices (it found several real bugs — act on its findings).

### Current focus: 6.9 original-style strategy screens (issues #98–#111, parent #112)

The user's direction (2026-11-12): the original Interceptor splits the strategy game
across many full-screen pages with its own art (CSD star map, Bases, Equip Ships,
Equipment & Personnel, Research, Base Stats, UFOpedia, Reports, Briefing/Debriefing,
Options, dialogs such as Interceptor Orders / Launch Mission / Alien Transmission). The
grid layout is fine for testing; the original style must be supported. "There are
additional screens, these are just a subset." Spec: `docs/specification/requirements/
interface.md` (R-UI-001…040), format in `design/format-interface.md` "Screen sets",
plan "6.9" on the Stage 6 page.

**Built (0.17.0–0.17.1):**
- `content::screens`: `screens.<id>` widgets may be full widgets `{kind, rect, images,
  action, value/source/text, size, colour, align, label, shape}`; kinds image, button,
  value, text, list, map (`shape: round`; `source: minimap`), info; actions
  `open(<screen>)`, `back`, `speed(n)`, `save`, `menu`, `testbed`; `dialog: true`;
  `open()` targets validated. `campaign.strategy_screen` names the first screen.
- `app::strategy`: `draw_set` keeps a stack of open screens (dialogs over screens),
  scales each design space like cockpits (`hud::Layout`), caches images; `draw_grid` is
  the testbed layout (Ctrl+T or a `testbed` button switches). Values: date, date_long,
  weekday, time, money, score, base, speed, selection. `--strategy --screen <id>` opens a
  screen (testbed/screenshots).
- `packs/interceptor/rules/screens.yaml`: csd, bases, equip_ships, purchase,
  manufacture, research, base_stats, ufopedia, reports over `original:WrappersDLL.dll#<id>`
  art with positions from the exe (verified) or measured (DERIVED).

**Reverse-engineering results** (facts only, no original content): `notes/re/wrappers/`
— `catalogue.md` (all 581 WrappersDLL image ids by screen/role), `screens.yaml` (every

## 4. Useful commands

```sh
cargo build --release
target/release/openinterceptor --campaign default --check --no-original
target/release/openinterceptor --campaign interceptor --check          # needs resources/xcom-cd
target/release/openinterceptor --campaign interceptor --strategy --screen csd --screenshot /tmp/x.png --frames 30
target/release/openinterceptor --campaign default --no-original --strategy --chapter 5
target/release/openinterceptor --campaign default --balance --no-original
target/release/openinterceptor --campaign default --no-original --strategy-soak 300
target/release/openinterceptor --write-schemas schemas                  # after schema changes (the gate checks)
./scripts/check.sh                                                      # the gate
python3 tools/build_bundle.py --no-settings                            # macOS app bundle
```

Screenshots of the running app (`--screenshot`) are the way to check visuals without a
human; note that screenshot runs are unthrottled, so time-based scenes advance slowly
per frame.
